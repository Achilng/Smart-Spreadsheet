# 七万条记录的隔离内存实验

日期：2026-10-29。结论：批量标签的撤销记录存在已测得的优化空间；搜索也受内存预算影响，但本轮没有验证出可直接上线的搜索优化。

正式应用代码未修改。以下数字来自组件级实验，不能解释为整个桌面应用的占用，也不能等同于用户电脑内存达到 96% 时的体验。

## 测试方法与边界

- 使用本机已运行的 Docker Desktop、已有 Rust/Node 镜像，每次只运行一个测试容器。没有拉取新镜像或升级系统、Node、Docker。
- 测试限额为 128、256 或 768 MiB，2 个 CPU；编译单独限制为 1 GiB。根文件系统只读、网络关闭、禁用核心转储；内存和内存加交换空间限额相同，禁止容器使用交换空间。Docker 对这些参数的含义见[资源限额文档](https://docs.docker.com/engine/containers/resource_constraints/)。
- 不创建用于挤占内存的填充程序。压力来自真实工作负载超出容器预算。宿主可用内存低于 3 GiB 时停止/拒绝测试；已记录运行的最低可用内存为 3,650.5 MiB，没有触发宿主内存保护。
- 所有主动创建的模拟数据、依赖副本、编译产物和临时脚本均放在 `D:/Agent/Agent_temp/memory-lab-20261029/`。Docker 本身已配置数据目录为 D 盘。不使用真实资料库或原图。
- 数据库样本为 70,000 条记录，六项可搜索文本平均约 2,186 UTF-8 字节，SQLite 文件约 600.2 MiB；完整性检查通过。没有图片文件。
- 后端直接编译项目数据库模块及所需辅助模块。JS 侧使用实际 `history.ts`、`mutableRowState`，将数据库返回值和状态容器替换为受控适配器。
- 源码采集基点为 `b0a6f3bc529d46a7d4c3f1c8bf0d4cb1a965f03f`，每份来源另有 SHA-256。测试期间其他聊天提交的 UI 动画改动不属于本实验。

这里验证的是**受限预算下的内存需求、完成情况和局部耗时**。没有运行 Windows WebView2、渲染、GPU、原图解码或系统换页测试。Linux 容器使用 Windows 绑定目录，磁盘耗时包含跨系统文件访问开销，不能把以下秒数作为用户电脑的预期速度。

## 批量标签：有明确收益的方向

操作：对同一组记录连续执行三次添加标签，保留三份撤销历史，然后撤销并重做最后一次；每种配置独立重复两次。

原逻辑在修改前后读取记录，将提示词、备注、画师、分组与标签一起保留，并用 `JSON.stringify` 比较两份状态。实验方案只返回、保留行编号与标签。实验方案尚未实现正式的投影查询接口、事务与跨窗口同步。

| 场景 | 原逻辑 | 只记录标签的实验方案 |
|---|---|---|
| 10,000 条，768 MiB 容器限额 | 两次完成；进程峰值 RSS 346.7 / 353.1 MiB | 两次完成；进程峰值 RSS 77.5 / 77.2 MiB |
| 10,000 条，256 MiB 限额 | 两次均在第三轮记录历史时被 OOM 终止 | 两次完成；峰值 72.8 / 72.7 MiB，撤销与重做检查通过 |
| 70,000 条，768 MiB 限额 | 两次均在第一轮读取修改前状态后、历史记录完成前被 OOM 终止 | 未测此限额 |
| 70,000 条，256 MiB 限额 | 两次均被 OOM 终止 | 两次完成三轮及撤销/重做；峰值 168.3 / 167.8 MiB |

同为 768 MiB 预算时，一万条场景的进程峰值减少约 78%。这不表示整个应用能减少 78% 内存。进程 RSS 含共享页，不能与 cgroup 计费内存直接混用；是否被内存限额终止以 Docker `State.OOMKilled` 为准，而非仅看退出码 137。

最终适配器直接生成独立、平铺的文本字符串，没有为模拟 IPC 额外执行整批 JSON 序列化/解析。真实数据库与 IPC 的成本未计入。实际历史函数自身的 `JSON.stringify` 保留。Node 在各组均设置 `--max-old-space-size=640`，因此这里不是 WebView2 默认堆策略的测试。

初步版本曾额外模拟序列化，产生不必要的副本；这些结果保存在证据包的 `results/pilot-js/`，已全部排除，不参与表格和结论。

## 搜索与保存：内存边界被复现，优化尚未验证

| 后端配置 | 两次运行结果 |
|---|---|
| 现有 `temp_store=MEMORY`，768 MiB 限额 | 均完成全部操作；首次搜索后进程 RSS 约 154.6 MiB，全部流程峰值约 196.5 MiB |
| 现有逻辑，128 MiB 限额 | 均能打开库、显示首页；随后停在首次搜索，180 秒超时保护终止；`OOMKilled=false` |
| 仅改为 `temp_store=FILE`，128 MiB 限额 | 均在首次搜索报 SQLite 扩展错误 1546，未得到有效的内存/速度对照 |

在 768 MiB 两次基准中：首次搜索约 15.5 秒，无结果搜索约 23 秒；单条备注的数据库写入约 4–8 毫秒，但后续标签/列表/详情刷新约 14.5 秒。批量一万条标签的数据库写入约 13.4–14.2 秒，后续刷新又约 14.5–15.0 秒。命中数量分别为 `painter42=722`、不存在的词为 0、`white dress=70,000`；标签实际增加 10,000 个关联。

这些磁盘相关耗时受 Docker/Windows 绑定目录影响很大，**不能作为原生 Windows 性能结论**。它们能帮助定位“写入”和“保存后的刷新”是不同阶段；应在原生环境继续测量刷新是否需要执行。128 MiB 的超时也不能写成应用发生了 OOM 崩溃。

错误 1546 是 `SQLITE_IOERR_TRUNCATE`，表示改变文件大小时的文件系统层错误，见 [SQLite 错误码说明](https://www.sqlite.org/rescode.html#ioerr_truncate)。它是本次落盘实验的阻碍，不能据此宣称落盘缓存已经有效，也不能断言原生 Windows 会遇到同样问题。

## 建议的开发顺序

1. **先做标签专用撤销与查询。** 数据库只返回受影响标签，撤销只恢复相关标签；避开无关提示词的读取和整批字符串比较。保留原有失败回滚、撤销/重做与选区冻结行为。
2. **再限制历史记录的总占用。** 现有 50 次上限不能约束单次大批量操作；可按大小设预算，或把较大的历史放到资料库中。具体阈值需要真实数据验证。
3. **减少不必要的保存后刷新。** 根据修改字段、当前搜索/筛选/排序判断是否重新查列表、更新标签统计。不能一律跳过刷新，否则会留下错误的筛选结果。
4. **单独验证搜索方案。** 值得评估可控缓存或持久化搜索索引，但需要原生 Windows 的数据库测量，以及中文、子串、分隔符匹配、跨窗口编辑与缓存失效验证。本轮不建议直接全局改 `temp_store`。

即使完成这些优化，也不能保证整个系统内存耗尽时操作始终流畅。本轮证明的是可以明显减少部分工作负担，并非确认了那位用户所有卡顿的唯一原因。

## 证据与排除项

- [原始测量与运行状态](results.json)：包含 21 次运行的配置、阶段日志、错误、宿主余量、源码哈希与数据特征。
- [实验源码和完整日志包](benchmark-evidence.zip)：包含独立 Rust 源码、JS 对照、运行器、锁文件与 `REPRODUCE.md`；不含模拟数据库、编译产物或依赖缓存。
- 准备模拟库时，Rust 在绑定目录的写入超过 300 秒，被保护机制停止在 38,500 条；本机 Python 完成到 70,000 条后检查完整性。这不算应用低内存失败。
- 一次 256 MiB 后端试跑为缩减重复矩阵主动停止，没有纳入结果。
- 没有新增单元测试，没有修改正式应用代码，也没有替换桌面安装版。
- 测试容器全部退出并移除。归档后，自动审批拦截了临时目录清理；改为只删除两份已核对路径的模拟数据库也被拦截，返回原因均只有“策略阻止”。未改用其他方式绕过，因此 D 盘临时目录仍保留，正式报告和证据包已独立保存。
