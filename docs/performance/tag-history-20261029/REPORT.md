# 标签历史与按需刷新：实现及验证

日期：2026-10-29。对应前期调查：`../memory-pressure-20261029/REPORT.md`。

## 已落地的行为

- 详情页单张加减标签与批量标签窗口共用新的事务接口。数据库先固定操作选区，再记录实际新增、删除的“标签—图片编号”关联，修改与记录一起成功或一起回滚。
- 标签撤销、重做只恢复这些关联，不读取或保存无关提示词、备注、分组。不撤销原本已有的同名标签，也不覆盖操作之后的无关字段变化。空变更不添加历史。
- 普通、无筛选、按时间排序的列表中，修改备注/提示词/标签后只更新缓存中相关行和当前详情。文本修改不刷新标签统计；标签修改仍刷新统计。关联视图缓存与工具箱通知继续更新。
- 搜索、标签/高级筛选、去重、分组展示、隐藏已分组及最近更新排序继续走完整查询。缓存中需要回读超过 201 行、正在加载分页、列表有错误等情况也回退完整查询。异步回读核对查询代次、活动行与同步代次，防止过期数据覆盖。
- 保留原来最多 50 项撤销历史；未降低图片清晰度或图片并发，未改变搜索匹配和搜索缓存，未添加需要用户切换的性能模式。

## 隔离内存测量

使用已有 Docker，单次一个容器，256 MiB 硬限额、禁用交换空间、2 CPU、宿主剩余内存低于 3 GiB 停止。没有用占位程序填满电脑内存，没有访问真实图库，没有升级环境。

前端使用本轮 `history.ts` 的实际函数，经 TypeScript 转译执行；IPC、任务提示和界面刷新使用适配器。标签响应使用实际后端返回的数据形状，经过 JSON 编解码；模拟数据层继续保留标签状态。每次连续三轮添加标签，再完整撤销三轮、重做三轮，并检查无变化时不增加历史。

| 每轮图片数 | 运行次数 | 测试进程峰值 RSS | 256 MiB 内结果 |
|---|---:|---:|---|
| 10,000 | 2 | 70.2–70.5 MiB | 均完成，撤销/重做正确 |
| 70,000 | 2 | 113.9–114.6 MiB | 均完成，撤销/重做正确 |

前期原有整行历史基准：10,000 条、三轮时峰值 346.7–353.1 MiB（768 MiB 限额），256 MiB 下两次均 OOM。该旧结果来自前期报告；本轮没有重跑旧基准。两轮的被测历史代码与响应形状不同，方向可比较，但不是相同内存限额下完整软件的 A/B 测试。

**这些数字不是整个应用的内存占用，也不是可以从任务管理器中直接减去的数值。** 本轮没有测完整 Windows/WebView2 在系统内存 96% 时的换页或帧率。前端耗时包含用于采样的主动等待，不用来宣称桌面响应快了多少倍。

## 后端与界面验证

- `npm run build`（含 TypeScript 检查）通过；`cargo check --locked -p smart-spreadsheet` 通过；现有标签数据库测试 19 项全部通过；`git diff --check` 通过。
- 临时 Rust 集成程序直接编译项目数据库模块：验证大小写、名称去空白、重复编号、已有标签、混合增删、无变化、保留无关标签/备注/分组、筛选选区排除项、撤销重做。
- 故障注入：第二个标签插入触发 SQLite ABORT 时，第一个标签与定义也完整回滚；历史操作第二组包含不存在的行时，第一组已执行的修改回滚。
- 70,000 条短文本模拟记录存于 SQLite 内存数据库，256 MiB 限额下三轮修改、三轮撤销与重做成功；进程峰值约 67.7 MiB。单轮增加标签约 227–270ms，返回 JSON 408,979 字节。**此项隔离了事务和变更记录成本，不能与前期 Windows 绑定目录上长文本库的磁盘耗时直接比较。**
- 浏览器模拟图库：详情标签添加、撤销、重做；两张图片批量同时增删标签、撤销、重做；保存失败保留待办、重试成功后禁止再次应用；标签筛选中移除标签立即从结果消失，撤销后恢复。
- 备注/提示词普通保存没有 `query_rows` 或 `list_tags`；无筛选两张图片批量编辑只回读选中的两行及当前详情。搜索中修改提示词使其不再命中，结果从 1 变 0；最近更新排序保存备注仍发起 `query_rows`。
- 浏览器异步集成检查：拦住旧回读，再完成新修改和新回读，释放旧请求后新内容仍保留；刷新途中切换到空结果搜索不会回到原列表。202 行缓存变更直接回退，没有调用过量回读。
- 核对关联视图刷新、`main://library-changed` 工具箱通知仍发出；未将模拟通知冒充真实多窗口端到端测试。
- 1440×900 详情与批量窗口、900×600 标签窗口均检查过截图；主要操作可见，无新遮挡或横向溢出。界面使用模拟图片，不访问真实图库。

过程中一次浏览器脚本尝试点击“最近更新”列表中尚未渲染的第 1 行而超时；改为实际首张图片后完成检查。一次批量上限检查误把关联视图通知计入行回读，收窄到 `get_rows_by_ids` 后确认无额外读取。这两项为验证脚本修正，不是隐瞒的应用失败。

## 证据、复现及限制

- `results.json` 保存 4 次前端限额运行状态、阶段日志及后端测量输出。
- `evidence.zip` 保存临时驱动脚本、转译历史、后端源码快照、锁文件、QA 清单及截图；不包含依赖缓存、浏览器配置、数据库或二进制。
- `prepare-node.cjs` 从项目提取最新历史代码；`run.py` 运行限额前端测量。后端用证据中的 Cargo 项目在现有 `rust:latest` 镜像中编译后运行 `memory-lab 70000`，同样指定 `--memory 256m --memory-swap 256m --network none`。依赖复用本机已有缓存，不需要升级 Node。
- 真实用户机器的搜索缓存、其他程序挤占内存与磁盘换页仍可能卡顿。此次改动去掉了标签历史的大量无关数据处理，未承诺解决所有卡顿，也未发现需要牺牲既有功能的取舍。
- 测试容器均已退出并移除，测试浏览器已关闭；临时工作留在 D 盘，不执行额外清理。未新增仓库单元测试、未发布安装包。
